## 1. 📁 推奨プロジェクトフォルダ構成

プロジェクトのルートディレクトリは、**「利用者が知りたい情報（利用者視点）」**と**「開発・保守に必要な情報（開発者・AI視点）」**を明確に分離して整理します。

```text
project-root/
├── README.md                  # [必須] プロジェクトの顔。利用者向けメインドキュメント
├── LICENSE                    # [推奨] ライセンスファイル
├── .gitignore                 # [必須] Git追跡除外設定
├── docs/                      # [推奨] 利用者向け補足ドキュメント・静的アセット（画像・図）
│   ├── USERS_GUIDE.md         # 利用者向け詳細ガイド（READMEに収まらない使い方・設定）
│   ├── DEVELOPERS_GUIDE.md    # ビルド・開発環境構築・カスタマイズ手順
│   ├── FAQ.md                 # よくある質問・トラブルシューティング
│   └── *.png / *.gif          # ドキュメント用画像アセット
├── dev/                       # [Git追跡] 開発者・AI専用資料・運用スクリプト
│   ├── templates/             # defaultプロジェクトから複製したテンプレート一式
│   │   ├── PROJECT_RULE.md     # [本ファイル] プロジェクト全体の基本方針
│   │   ├── RELEASE_RULE.md     # リリース・配布の基本方針
│   │   ├── README_SAMPLE.md    # READMEの書き方テンプレート
│   │   ├── release-Sample.ps1  # リリーススクリプトのテンプレート
│   │   └── .gitignore-Sample   # .gitignoreのテンプレート
│   ├── README.md             # 現在の対象版と資料の目録
│   ├── history/              # 過去・進行中・未来すべての版別記録
│   │   └── v0.0.1/
│   │       ├── v0.0.1-req.md
│   │       ├── v0.0.1-imp.md
│   │       ├── v0.0.1-task.md
│   │       └── logs/         # 動画・生ログ・録画台帳・生成結果。Git対象外
│   ├── research/             # 版に属さない調査・検討。対象ごとに配置
│   └── scripts/               # テスト・ビルド・リリース・サンプル生成スクリプト
│       └── release-<アプリ名>.ps1
├── src/                       # [必須] ソースコード本体
├── release/                   # [Git対象外] リリース成果物の出力先（ローカル）
│   └── Publish/               # GitHub Releasesに公開したバイナリの控え
│       ├── *.zip              # ZIP（ポータブル）版
│       └── *_Setup.exe        # インストーラ版
├── samples/                   # [Git追跡・任意] 表示・回帰確認用サンプルデータ
└── tools/                     # [任意] 開発・テスト補助ツール
```

> **ルート md は最後に。** 利用者が最初に見る `README.md` をルートに置き、
> 詳細は `docs/` 内の各ドキュメントに誘導することで、ルートディレクトリをクリーンに保ちます。それ以外の説明は `docs/` や `dev/` に振り分けます。

## 2. 🗺️ 資料の配置

| 内容 | 配置 |
|---|---|
| 利用者の入口 | README.md |
| 現行仕様・操作説明・再現可能な手順 | docs/ |
| 継続的なルールと目録 | dev直下。共通テンプレートはdev/templates/ |
| 版に属する要求・計画・設計検討・実装報告・テスト結果・リリース結果 | dev/history/vX.Y.Z/。進行中・未来・完了済みを問わず最初からここに作成 |
| 版に属さない調査・検討・未確定案 | dev/research/<対象>/ |
| テスト動画・生ログ・録画台帳・実行時の生成結果 | dev/history/vX.Y.Z/logs/<実行識別子>/。Git対象外 |

版別の正本は同じ版フォルダーの `vX.Y.Z-req.md`、`vX.Y.Z-imp.md`、必要な場合だけ `vX.Y.Z-task.md` とする。次版へ進むときは新しい版フォルダーを作り、旧版は移動しない。historyは完了済み専用ではない。

新設前に正本と参照元を確認し、文書やフォルダーを機械的に増やさない。生成スクリプトも対象版から出力先を決め、dev直下や独立したtest-videosへ生成しない。researchにログ用フォルダーは設けない。既存資料の移動・統合は別途依頼された範囲で行い、内容・参照・生成元を保存する。

## 3. 🚫 `.gitignore` の基準と対象方針

個人開発において、リポジトリに**「入れるべきもの」**と**「除外（gitignore）すべきもの」**の明確な基準です。
本プロジェクト構成では、**`dev/`（開発資料）と `samples/`（回帰確認資料）はGitで追跡**し、
`release/`（配布成果物）、ビルド成果物、認証情報、ローカル一時データをGit対象外とします。

### ❌ `.gitignore` に追加して除外するもの

1. **リリース成果物（`release/` 全体）**
   - `release/`・`release/Publish/` の `*.zip` / `*_Setup.exe` などの配布バイナリ。配布は GitHub Releases で行う。
2. **ビルド成果物・中間生成物**
   - `target/`, `node_modules/`, `dist/`, `build/`, `*.exe`, `*.dll`, `*.so`
3. **ローカル環境変数・認証情報**
   - `.env`, `.env.local`, `secrets.json`, APIキーが含まれる設定ファイル
4. **ローカルの大容量データ・学習モデル**
   - 大容量モデルファイル（`*.onnx`, `*.gguf`, `*.bin` など。※ダウンロード手順を `docs/DEVELOPERS_GUIDE.md` に記載する）
5. **OS・エディタ固有のキャッシュファイル**
   - `.DS_Store`, `Thumbs.db`, `.vscode/`, `.idea/`, `*.suo`
6. **ログファイル・実行時一時データ**
   - `*.log`, `/dev/history/*/logs/`, `*.sqlite` (テスト用ローカルDB), `tmp/`。版別報告のMarkdownは追跡する

### ⭕ 必ず Git にコミットして追跡するもの

1. **ソースコード（`src/`）と利用者向けドキュメント**
   - `README.md`, `LICENSE`, `docs/`（`USERS_GUIDE.md` / `DEVELOPERS_GUIDE.md` / `FAQ.md`）。
2. **開発資料と回帰確認資料**
   - `dev/` の要求・実装・進捗・履歴・運用スクリプトと、`samples/` の表示確認資料。
3. **ロックファイル**
   - `Cargo.lock`, `package-lock.json`, `pnpm-lock.yaml`（依存関係のバージョン再現性を保証するため）。
4. **`.gitignore` 本体・ビルド設定**
   - `.gitignore`, `Cargo.toml`, `package.json`, `installer.iss` などのプロジェクト設定ファイル。

> **⚠️ `dev/` を追跡する運用上の注意**
> `dev/` には認証情報、個人情報、ローカル専用の秘密鍵を保存しません。
> 必要なローカル設定は、原則としてWindowsの資格情報や環境変数に格納し `.env` などには保存しません。何を保存すべきかは目録を作ること。

## 5. 💬 コミットの運用ルール (Commit Conventions)

個人開発では、コミットログを後から検索・追跡しやすくするために **Conventional Commits（簡略版）** のプレフィックスルールを採用します。

### 5.1 コミットメッセージのフォーマット

```text
<type>: <要約（日本語でOK）>

[オプション: 詳しい変更理由や背景]
```

### 5.2 おすすめの `<type>` 一覧

| プレフィックス  | 意味・用途                                   | 例                                                |
| :-------------- | :------------------------------------------- | :------------------------------------------------ |
| **`feat:`**     | 新機能の追加                                 | `feat: 範囲指定キャプチャ機能を追加`              |
| **`fix:`**      | バグ修正                                     | `fix: 設定画面の保存ボタンが反応しない問題を修正` |
| **`docs:`**     | ドキュメントの変更                           | `docs: READMEに推奨フォルダ構成の説明を追記`      |
| **`style:`**    | コードの意味に影響しない整形・タイポ修正     | `style: インデントの微調整とコメントの誤字修正`   |
| **`refactor:`** | バグ修正や機能追加を含まないコード再構築     | `refactor: OCR処理モジュールを分離`               |
| **`chore:`**    | ビルドプロセスや設定ファイル・依存関係の更新 | `chore: Cargo.tomlの依存ライブラリを更新`         |

### 5.3 コミットの適切な粒度

- **「1機能 / 1バグ修正 = 1コミット」** を基本とします。
- **「ビルドとテストが通る状態」** でコミットします。動かない状態でコミットを重ねないようにします。

## 6. 🚀 リリース手順・配布フロー (Release Management)

個人開発アプリのリリースをスムーズに行うための4ステップ手順です。

### 6.1 バージョニングルール（セマンティックバージョニング）

`vMAJOR.MINOR.PATCH`（例: `v1.2.0`）形式を採用します。

- **MAJOR**: 破壊的変更・大幅な互換性の変更（`v2.0.0`）
- **MINOR**: 後方互換性のある機能追加（`v1.1.0`）
- **PATCH**: 後方互換性のあるバグ修正・軽微な調整（`v1.0.1`）

### 6.2 リリースの実施フロー

1. **バージョン表記の更新**
   - 設定ファイル（`Cargo.toml`, `package.json`, `installer.iss` 等）内のバージョン文字列を更新します。
2. **更新履歴の記録**
   - このリリースに含まれる変更点は、`dev/history/vX.Y.Z/vX.Y.Z-imp.md`（実装方針ファイル）に記録・集約します。
3. **ビルドと動作確認**
   - リリースビルドコマンドを実行し、インストーラまたは配布用パッケージが正常に動作するか確認します。
   ```bat
   cargo build --release
   "C:\Program Files (x86)\Inno Setup 6\ISCC.exe" installer.iss
   ```
4. **Git タグの打刻と Push**
   ```bash
   git add .
   git commit -m "chore: release v1.2.0"
   git tag v1.2.0
   git push origin main --tags
   ```
5. **GitHub Release の作成**
   - GitHub でタグ `v1.2.0` に紐付くリリースを作成し、`vX.Y.Z-imp.md` の内容とインストーラー（`<アプリ名>_v1.2.0_Setup.exe`）やZIPを添付して公開します。
   - （`dev/scripts/release-<アプリ名>.ps1` を作成してビルド〜公開を半自動化することを推奨。手順の詳細は `dev/templates/RELEASE_RULE.md` を参照）

## 7. 🛡️ 個人開発のその他ベストプラクティス

### 7.1 ブランチ戦略（個人開発向け）

- **基本は `main` ブランチ運用**: 一人での開発の場合、過度なブランチ分岐はオーバーヘッドになります。
- **機能ブランチ (`feature/xxx`) を使うケース**:
  - 数日〜数週間かかる大規模な機能追加や、壊れる可能性のある大規模リファクタリングを行う場合はブランチを切って開発します。

### 7.2 秘匿情報（APIキー等）の漏洩防止対策

- **APIキーは絶対直書きしない**: ソースコードにAPIキーを直接書かない。
- **ローカルでのテスト用キー管理**: 設定画面UIから入力させて暗号化保存するか、`.env` ファイル（`.gitignore` 済み）を使用。
- **間違えてコミットした場合**: 即座に該当APIキーを無効化（Revoke）して再発行する。

### 7.3 アイデア・タスク管理

- 設計が固まっていないアイデアはコード内に放置せず、`dev/research/<対象>/` や GitHub Issues にリスト化して書き出します。
- 提案する必要ないアイディアは `dev/research/<対象>/` に記述する。
- 開発で得られた技術知見は `dev/research/<対象>/` に記述する。

## 8. 📋 新規プロジェクト開始時チェックリスト

新しくプロジェクトを始める際は、以下の手順でディレクトリとドキュメントを初期化します。

- [ ] `default` プロジェクトの `dev/templates/` から一式（`PROJECT_RULE.md` / `RELEASE_RULE.md` / `README_SAMPLE.md` / `release-Sample.ps1` / `.gitignore-Sample`）を、新プロジェクトの `dev/templates/` に複製する。
- [ ] `.gitignore-Sample` を基に `.gitignore` を作成し、`dev/`・`docs/`・`samples/`が追跡対象、`release/`・ビルド成果物・秘匿情報が除外対象になっているか確認する。
- [ ] `README_SAMPLE.md` をコピーして `README.md` を作成し、中身をプロジェクトに合わせて修正する。
- [ ] `docs/` を作成し、`USERS_GUIDE.md` / `DEVELOPERS_GUIDE.md` / `FAQ.md` を配置する。
- [ ] `dev/README.md`から対象版を案内し、`dev/history/vX.Y.Z/`に必要な要求・計画・進捗資料を作成する。版に属さない調査は必要になった時点で`dev/research/<対象>/`へ置く。
- [ ] `dev/scripts/` に `release-<アプリ名>.ps1` を配置する（`release-Sample.ps1` を複製・調整）。
- [ ] `src/` にソースコードの初期構造を作成する。

## 9. 本PCのMSIX共通署名

本PCの現在のWindowsユーザーで開発するアプリは、Store外MSIXの署名に共通の`CN=KotorinChunChun`証明書を使う。
秘密鍵は`CurrentUser\My`に保持し、`%LOCALAPPDATA%\KotorinChunChun\MSIX\signing.json`の拇印で固定する。
新規アプリでは同梱の`MSIX_SIGNING.md`を読み、`MsixSigning.psm1`をプロジェクトの署名スクリプトへ組み込む。
個別証明書の自動発行、PFX・パスワードのrepo保存、共通設定がない場合の別キーへのフォールバックはしない。
既存Publisherの変更では更新・設定移行を確認し、Store提出用IdentityとMicrosoftの署名経路は維持する。
リリース・公開・信頼登録・インストール・秘密鍵バックアップは、それぞれの明示的な依頼に従う。
