# 文書の編集方針

## 読み手ごとに分ける

| 文書 | 書く内容 | 書かない内容 |
| --- | --- | --- |
| ルートREADME | 何ができるか、動作環境、配布物の入手、最初の操作、説明書への入口 | ソース取得、ビルド、内部構造、実装予定、進捗、試験件数、公開作業の報告 |
| docsの利用者向け資料 | 現在の画面での操作、設定、データ保持、エラーと対処 | 開発用コマンド、製品内部の型・通信仕様、実装作業の経緯 |
| docsの開発者向け資料 | 再現可能な環境準備、仕様、検証手順、配布条件 | 特定PCでの作業進捗や、過去の試験を今回の実測として書くこと |
| dev/history/vX.Y.Z/ | その版の要求・計画・判断・検証結果・公開結果 | 現行手順の正本をここだけに置くこと |
| dev/README.md | 継続規約と版別記録への目録 | 利用者向けの操作説明を重複掲載すること |

READMEは利用者向けの説明書とする。開発用情報は開発者ガイドへのリンクだけを置き、本文に開発・進捗の節を増やさない。新しいアプリのREADMEを作るときも同じ方針を使う。

## 版と公開状況

- ダウンロードはReleasesへの入口を案内し、古い特定版を「最新」として固定しない。
- 版固有の制限を説明する場合は対象を明記する。ソースの実装、公開配布物、インストール済みの機能を区別する。
- 一覧の追加・公開状態・対応操作は配信用定義や画面で確認できるようにする。固定件数や「今回追加しました」という進捗をREADMEに残さない。
- 未実装・検証済み・公開済みという記載は根拠を確認する。過去の報告を現行の対応状況へ読み替えない。

## 更新するとき

1. 既存の正本・参照元とGit差分を確認する。管理対象アプリは独立Gitのため、別作業の変更をまとめて取り込まない。
2. 利用操作・開発手順・版別記録を上の表に沿って分ける。既存の文書パスは可能な限り保持する。
3. 操作説明は実際のボタン名・有効条件と照合する。開発コマンドはスクリプトやソースを確認し、推測で載せない。
4. 開発手順を移したら、目次・開発者ガイド・参照元を更新する。過去の報告は版別記録を参照し、実測値を現行説明へコピーしない。
5. リンク・見出し・差分を検査する。文書だけの変更では製品ビルドやGUI試験を形式的に実行しない。

子リポジトリの利用説明は、各アプリの公開ページやマニュアルを正本とする。本体READMEへ子のビルド・開発進捗を転載しない。未公開の子には推測した公開URLを付けない。
